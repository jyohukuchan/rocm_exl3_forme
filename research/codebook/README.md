# EXL3-INT8 の数値型（符号語）探索

INT8 GEMM（WMMA iu8）で推論する前提で、EXL3 の「連続する値で 1 つの数を表す」方式（bitshift trellis）を保ったまま、
精度と decode 速度を両立する符号語を探した記録。LUT は「計算」と「表引き」の両方を候補にした。
参照: <https://github.com/lxe/dsx/blob/main/docs/t16.md>（T16）。

## 結論（要約）

1. **符号語の式で精度は上がらない。** K=4 の mul1 は理論下限の約 1.12 倍で、i.i.d. ガウス表（1.12 倍）に並ぶ。
   INT8 格子への丸めによる悪化もない。
2. **T16（16bit 乗算 + 2byte 和）は K=4 で使えない。** MSE が mul1 の約 1.5 倍（K=2 専用の設計）。
3. **速度を決めるのは符号語の式ではなく、タイル内の並びと総命令数。** 並びを WMMA の B フラグメント順にして LDS の
   往復を消すと +13%、乗算を 24bit 定数（フルレート）にするとさらに +4% で、上限（復号なし）の約 98% に届く。
4. **表引きは候補から外れる。** 精度は mul1 より 3〜4% 悪く、LDS の表引きは計算より遅い（-15%）。
5. 推奨: **符号語 `x = (s * 0xDCD12D) mod 2^32`、`B = x の 4 byte の和`、`q = (B - 509) >> 2`（INT8 格子は現行と同じ）、
   タイル内の並びは WMMA B フラグメント順**。再量子化が必要。decode は GEMM 単体で約 +18%、1 トークンでは +14% 前後の見積もり。

## 1. 精度（Viterbi シミュレーション、`viterbi_sim.py`）

i.i.d. ガウスのデータを 16bit 状態の bitshift trellis で Viterbi 量子化したときの MSE/分散（最適スケール）。
長さ 512 の系列 32 本、自由開始（tail-biting なし）。絶対値は資料より約 3% 高く出るが、比は資料と一致する
（K=2 の T16/mul1 = 1.044、資料は約 1.04）。

| 符号語（MSE / 理論下限） | K=2 | K=4 | 復号の中身 |
|---|---:|---:|---|
| mul1（32bit 乗算、4byte 和） | 1.060 | **1.117** | 乗算 1（4 分の 1 レート）+ dot4 + シフト |
| mul1 を INT8 格子 `(B-509)>>2` に丸める | 1.060 | 1.115 | 同上 |
| i.i.d. ガウス表（参照上限） | 1.062 | 1.121 | 65536 エントリの表 |
| T16（0x3A2F、2byte 和） | 1.103 | **1.672** | 16bit 乗算 + 2byte 和 |
| 24bit 乗算（0x3A2F）、4byte 和 | 1.084 | 1.283 | |
| 4 つの 16 エントリ表（nibble 単位、状態をスクランブル） | 1.111 | 1.164 | 表 4 回 + 加算 |
| 2 つの 256 エントリ表（byte 単位） | 1.099 | 1.154 | 表 2 回 + 加算 |
| popcount（32bit 積） | 1.114 | 2.451 | |
| 状態の下位 8bit（一様） | 1.932 | 7.719 | |

### 24bit 定数（`const_search.py`、`robust_check.py`）
`v_mul_u32_u24`（24bit 定数、フルレート 1 命令）で `x = (s * C) mod 2^32` を作る符号語の定数を探索した（K=4、121 個）。
mul1 に対する MSE 比:

| C | K=3 | K=4 | K=6 |
|---|---:|---:|---:|
| 0x7FD633 | 1.025 | 0.998 | 1.037 |
| 0x7CE42D | 1.012 | 1.001 | 1.061 |
| **0xDCD12D**（mul1 の定数の下位 24bit） | 1.015 | 1.007 | 1.022 |

K ごとのばらつきは数 % で、シミュレーションの誤差と同程度。1 本で全ビット幅を扱うため、最も安定した **0xDCD12D** を推奨する。

## 2. 速度（R9700、`decode_bench.hip`）

rows=1 の GEMV（N=34816、K=5120、4bit、重み 89 MB で最終レベルキャッシュ 64 MB を超える）。復号の方式だけを替え、
GEMM の骨格（先読み、WMMA、A の読み出し）は共通。乱数の trellis なので速度のみの比較。

| 方式 | GB/s | 現行比 |
|---|---:|---:|
| V0 タイル並び + LDS（現行、mul1） | 496 | 1.00 |
| V1 WMMA B フラグメント並び、mul1 | 561 | 1.13 |
| V2 WMMA B フラグメント並び、24bit 乗算 + dot4 | **585** | **1.18** |
| V3 同、24bit 乗算 + and + sad（6bit 欄の和） | 550 | 1.11 |
| V4 同、2 つの byte 表を LDS から引く | 477 | 0.96 |
| 上限（復号なし） | 598 | 1.21 |

- 24bit 乗算の効果は並びを替えた後で効く。単独で乗算を xorshift に替えても効かない（391→399 GB/s、実カーネルでの測定）。
- WMMA B フラグメント並びとは、ストリームの位置 `t = 8L + j` を `(列 n = L % 16、k = 8 * (L / 16) + j)` に置く並び。
  レーン L が復号した 8 個がそのまま WMMA の B フラグメントになり、LDS と同期が不要で、A 側の k の並べ替えも不要になる。
  量子化側は `tensor_core_perm` の差し替えだけ（`EXL3_TILE_ORDER=frag` で実験用に切り替えられる）。
- 表引き（V4）が遅いのは資料の見積もり（データ依存の LDS 参照は ALU 約 4 命令分）と一致する。v_perm による
  レジスタ内の表引き（V5）は未実装。1 回の v_perm で 4 重み分を引けるが、16 エントリの表には 2 回の perm と選択が要り、
  窓の整列も含めると命令数は計算方式と同程度の見積もりで、精度は 3〜4% 悪いため見送った（実測していない）。

### decode 全体への換算（見積もり、実測ではない）
shelf の Qwen3.8 27B の 1 トークンは約 42 ms で、EXL3 の GEMM が約 83%（GEMM 単体の測定値の合計から）。
V0→V2 の +18% をそのまま当てはめると約 -12.6% の時間、つまり decode は +14% 前後。

## 3. 並びを替えても量子化精度が落ちないか

- Gaussian の模擬は並びに依存しない（i.i.d. のため）。
- 実モデル（Qwen3.5-2B、実 Hessian）の層 0 の 6 モジュールで `proxy_err` の比（frag / 現行）は 0.999〜1.009、平均 1.003。
- 層 1 以降は比較できない。変換器が量子化済みの層を通して次の層の入力を作るため、現行の復号カーネル（旧並び前提）で
  frag 並びの重みを読むと入力が壊れる（比が 2〜24 倍に見えるのは並びの影響ではなく、この欠陥）。
- 資料（T16）は実 expert 24 個で列順の並びに替えても差なしと報告している。
- 27B 全体の KLD は未測定。

## 4. 次にやること

1. 量子化器と復号カーネルに符号語 `mul24`（定数 0xDCD12D）と frag 並びを追加（ネイティブ拡張の再ビルド）。
2. shelf のカーネルを frag 並びに合わせて書き換える（LDS と k スロットの並べ替えを削除）。
3. 27B を再量子化（2B の全層が約 9 分だったので 27B で約 2〜3 時間の見積もり）し、BF16 に対する KLD と速度を測る。

## 再現

```bash
cd research/codebook

hipcc -x hip --offload-arch=gfx1201 -O3 decode_bench.hip -o decode_bench && ./decode_bench
```
